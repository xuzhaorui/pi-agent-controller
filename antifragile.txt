#001 | 2026-08-03 | 🔥StressTest | 从“是否支持子代理”转向“是否需要可控的任务隔离”

【波动源】
架构讨论最初聚焦于扩展是否支持 Subagent，但进一步质疑发现，“子代理”可能只是框架包装出的复杂黑盒：父子 Agent 嵌套、私有通信协议和隐式调度会削弱可观测性与人工干预能力。

【原始应对】
先按功能清单确认官方扩展示例能够启动独立 pi 进程，并据此回答“支持子代理”。这个回答验证了实现可能性，却没有先拆解真实需求，也没有区分“需要任务隔离/并行执行”与“需要 Subagent 抽象”。

【增益提取】
- 技术选型先追问所需能力：上下文隔离、并行、角色约束、故障隔离，还是自治调度；不要从框架名词出发。
- 优先把代理执行建模为透明、可取消、可重放、有输入输出契约的普通任务；只有明确收益超过调度和观测成本时，才引入 Subagent 抽象。
- “支持”不等于“应该使用”：评估标准应包括事件流、过程日志、人工接管、资源预算、失败传播和确定性回放。

#002 | 2026-08-03 | 🔥StressTest | 用显式 Execution 契约替换 Agent Runtime 黑盒

【波动源】
现有项目虽然由确定性 Controller 驱动，但运行边界仍命名为 Agent Runtime，只返回最终 Result，过程事件没有进入 Controller 的持久化状态，除停止整个 Run 外也缺少针对当前工作的显式干预入口。

【原始应对】
把 Worker 和 Reviewer 重构为有稳定身份的 Execution：Runtime 声明能力、标准化 Pi JSON 生命周期与工具事件、将事件写入 Run Journal，并增加查询与单次取消入口。当前实现诚实声明只支持 cancel，不伪装 pause 或 steer。

【增益提取】
- “可观测”必须进入领域契约和持久化日志，不能只存在于终端流式输出中。
- 控制能力采用 capability declaration；不支持就是显式 false，避免 UI 或上层逻辑制造虚假承诺。
- 干预当前 Execution 与终止整个 Run 是两个不同动作，应提供不同命令并让后续重试/阻塞继续受 Policy 控制。
